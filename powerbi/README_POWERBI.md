# دمج نموذج التنبؤ في لوحة Power BI

**تجمع مكة الصحي · إدارة الدورة الإيرادية وتحليل البيانات**

> النموذج **ثنائي**: يتنبّأ بـ«مقبولة بالكامل» مقابل «لم تُقبل بالكامل» (المرفوضة
> والمقبولة جزئياً معاً). عتبة التصنيف **0.45** على `p_not_fully_approved`.

هناك ثلاث طرق للدمج. الطريقتان الأولى والثانية تعرضان صفحة التنبؤ التفاعلية داخل
اللوحة، والثالثة تُدخل التنبؤات كأعمدة في نموذج البيانات نفسه — وهي الأقوى لبناء
مؤشّرات ومرئيات حقيقية.

---

## الطريقة ١ — تضمين الصفحة (الأسرع)

1. انشر مجلّد المستودع على GitHub Pages (ملف `.github/workflows/static.yml` الموجود
   ينشره تلقائياً عند كل دفع إلى `main`).
2. في Power BI Desktop: **Insert ← Web content**.
3. ألصق:

```html
<iframe src="https://<حسابك>.github.io/RCM/predict.html?embed=1"
        width="100%" height="900" frameborder="0"></iframe>
```

`embed=1` يُخفي الترويسة والتبويبات ويعرض نموذج الإدخال والنتيجة وأرجح أسباب الرفض
في عمود واحد مضغوط. أضف `&bg=transparent` لتبنّي خلفية مربّع اللوحة.

> صفحة التنبؤ تعمل بالكامل داخل المتصفّح — الأشجار وقيم SHAP تُحسب محلّياً ولا
> تُرسل بيانات المطالبة إلى أي خادم.

---

## الطريقة ٢ — تمرير المطالبة المحدّدة إلى الصفحة (ديناميكي)

اجعل الصفحة تستجيب للصف الذي يختاره المستخدم في اللوحة.

1. استورد جدول المطالبات عبر الطريقة ٣ أدناه (فهي تولّد أعمدة `*_Key` المطبَّعة).
2. أنشئ المقياس `رابط التنبؤ` من `powerbi/measures.dax` وعدّل `BaseUrl`.
3. أضف مرئي **HTML Content** (من AppSource) واربطه بالمقياس `مرئي التنبؤ HTML`.

عند اختيار المستخدم لمطالبة في أي جدول أو مصفوفة، يُعاد بناء الرابط وتُحدَّث الصفحة
وتشغّل التنبؤ تلقائياً (`auto=1`).

### معاملات الرابط المدعومة

| المعامل | الوصف | مثال |
|---|---|---|
| `total` | إجمالي الفاتورة | `1250` |
| `visitType` | نوع الزيارة | `er` · `opd` · `ip` |
| `hospital` | اسم المستشفى المطبَّع | `al noor specialist hospital` |
| `clinic` | اسم العيادة المطبَّع | `emergency` |
| `contract` | اسم العقد المطبَّع | `hajj1447` |
| `nphies` | نتيجة فحص الأهلية | `eligible` · `error` · `out_network` |
| `icd` | رمز ICD-10 كاملاً | `J06.9` |
| `triage` | CTAS من 1 إلى 5 | `3` |
| `gender` | الجنس | `Male` · `Female` |
| `nationality` | الجنسية المطبَّعة | `saudi` |
| `patientClass` | تصنيف المريض | `hajj` · `umrah` · `saudi` |
| `visitDate` | تاريخ ووقت الزيارة | `2026-08-18T14:30` |
| `embed` | الوضع المضغوط | `1` |
| `bg` | خلفية شفّافة | `transparent` |
| `auto` | تشغيل التنبؤ فور التحميل | `1` |

القيم المطبَّعة كاملةً موجودة في `model/artifacts/model_bundle.json` تحت `options`،
ويولّدها سكربت Power BI في أعمدة `*_Key` جاهزة.

---

## الطريقة ٣ — تسجيل دفعي داخل Power BI (الموصى بها للوحات)

تُدخل التنبؤات كأعمدة في نموذج البيانات، فتستطيع بناء بطاقات ومخطّطات وتصفية
عادية عليها.

### الإعداد

1. ثبّت المتطلّبات في بيئة Python التي يستخدمها Power BI
   (**File ← Options ← Python scripting** لمعرفة مسارها):

   ```
   pip install pandas numpy lightgbm shap openpyxl
   ```

2. درّب النموذج مرّة واحدة (يُنتج ملفات `model/artifacts/`):

   ```
   python model/train_model.py --data data/ALL_GUARANTORS_FINAL.xlsx
   ```

3. في Power BI: **Home ← Get Data ← More… ← Other ← Python script**.
4. ألصق محتوى `powerbi/powerbi_script.py` بعد تعديل `REPO_DIR` و `DATA_FILE`.
5. اختر جدول **`scored`** من نافذة المعاينة ← **Load**.

### الأعمدة الناتجة

| العمود | الوصف |
|---|---|
| `pred_label` / `pred_label_ar` | النتيجة المتوقّعة: `Approved` أو `NotFullyApproved` |
| `confidence` | ثقة النموذج في التصنيف |
| `p_approved` | احتمال التحصيل الكامل |
| `p_not_fully_approved` | احتمال عدم التحصيل الكامل (المقياس الأهم) |
| `risk_band` | خطر منخفض (<0.45) / متوسّط (0.45–0.65) / مرتفع (≥0.65) |
| `billed_amount` | إجمالي الفاتورة |
| `expected_revenue` | الإيراد المتوقّع تحصيله |
| `amount_at_risk` | المبلغ المعرّض للخطر |
| `shap_top1..3` + `_value` + `_dir` | أقوى ٣ عوامل أثّرت في القرار واتجاه أثرها |
| `reason_top1..3` + `_code` + `_p` | أرجح ٣ أسباب لعدم القبول الكامل |
| `reason_top1_action` | الإجراء التصحيحي المقترح |
| `*_Key` | القيم المطبَّعة لبناء روابط DAX |

### مقاييس جاهزة

انسخ محتوى `powerbi/measures.dax` — يتضمّن المبلغ المعرّض للخطر، نسبة المطالبات
عالية الخطر، دقّة النموذج على المطالبات التي صدر فيها قرار فعلي، **استرجاع
المطالبات الخاسرة** (المؤشّر التشغيلي الأهم)، وفرصة التدخّل (المبلغ القابل
للإنقاذ في المطالبات المعلّقة عالية الخطر).

### التحديث الدوري

اضبط **Personal Gateway** لتحديث السكربت جدولياً. أعد تدريب النموذج كل ربع سنة
(أو عند تغيّر سياسات الضامنين) بإعادة تشغيل `train_model.py` على أحدث البيانات.

## بديل بدون Python داخل Power BI

إن تعذّر تفعيل Python في بيئتك، شغّل التسجيل خارجياً واستورد الناتج كملف عادي:

```
python model/score_batch.py --data data/claims.xlsx --out scored.csv
```

ثم **Get Data ← Text/CSV**. نفس الأعمدة، دون الحاجة إلى Python داخل Power BI.

## اقتراح تصميم اللوحة

| القسم | المرئي | الحقول |
|---|---|---|
| الصف العلوي | بطاقات KPI | المبلغ المعرّض للخطر · نسبة عالية الخطر · استرجاع المطالبات الخاسرة · فرصة التدخّل |
| يمين | مخطّط شريطي | المبلغ المعرّض للخطر حسب الضامن |
| يسار | مخطّط شريطي | المبلغ المعرّض للخطر حسب المستشفى |
| الوسط | مخطّط دائري / شريطي | توزيع `reason_top1` (أسباب عدم التحصيل المتوقّعة) |
| الأسفل | جدول تفصيلي | المطالبات مرتّبة تنازلياً حسب `amount_at_risk` مع تنسيق شرطي بـ `risk_band` |
| لوحة جانبية | HTML Content | صفحة التنبؤ للمطالبة المحدّدة (الطريقة ٢) |

اجعل الجدول التفصيلي مصفّى على المطالبات التي **لم يصدر فيها قرار بعد** — فتلك
وحدها هي النافذة التي ما زال التدخّل فيها ممكناً.
